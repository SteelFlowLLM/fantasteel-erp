## 화면 페이지 틀

각 화면 페이지는 같은 순서로 씁니다.

1. 목적·사용 역할·필요 권한
2. 철강 흐름에서의 위치 (받는 것 → 넘기는 것)
3. 화면에 표시할 데이터
4. 사용자 동작 → API
5. 상태 변화·작업 로그
6. 연결 화면·확인 필요

### 🧭 화면별 상호작용·데이터 정리

<aside>
📌

**작성 방식**: 메뉴별로 화면을 구성하는 요소(버튼·입력·표·탭·패널)마다 사용자가 무엇을 하면 어떤 코드가 실행되고, 어떤 API와 서버 처리를 거쳐 화면이 어떻게 바뀌는지 적는다. 역할마다 같은 형식으로 토글을 추가한다.

**기준**: 화면 구성은 화면 설계서 프로토타입 B안(10 수주 목록, 11 수주 등록, 12 수주 상세, 23 출하요청 등록, 24 출하요청 배정), 동작은 요구사항 정의서·업무 프로세스 정의서, API는 업무 프로세스 12.2절을 따른다. 코드 이름(훅·서비스·파일)은 코드 컨벤션 규칙에 맞춘 **제안 이름**이며, 저장소 코드와 다르면 저장소가 맞다.

**표기**: 🟡 = 12.2절에 없어 새로 제안하는 API / ⚠️ = 프로토타입이 요구사항과 달라 화면을 고쳐야 하는 곳

</aside>

    **저장 시 서버 처리**
    
    ```
    POST /api/v1/sales-orders
    SalesOrderController.create(dto)          // CreateSalesOrderDto: orderedQty @IsInt @Min(1)
      └ SalesOrderService.create(dto, actor)
          prisma.$transaction(async (tx) => ...)
            1. 수주번호 채번 SO-YYMM-NNN (Asia/Seoul)
            2. sales_order, sales_order_item 저장 (톤은 저장하지 않음)
            3. 품목마다 라우팅으로 생산 경로 결정
            4. ReservationService.reserve(tx, item)
               - inventory 조건부 UPDATE: reserved_qty += n (가용 매수가 n 이상일 때만)
               - reservation ACTIVE 생성 (매수, LOT 미지정)
            5. 부족 매수가 있으면 ProductionPlanService.createForShortage(tx, item)
            6. businessEventRecorder.record(tx, ...)
               SALES_ORDER_REGISTERED(USER), RESERVATION_CREATED(SYSTEM), PRODUCTION_PLAN_CREATED
            7. 업무방(chat_room WORK) 생성, 생산 부서 알림
      └ toSalesOrderResponse(): 톤 계산값 추가, Decimal → 문자열
    ```
    
    7번 업무방 자동 생성은 프로토타입 동작이고, 요구사항에는 "업무방은 수주에 연결"까지만 있다 🟡
