# 불합격 관리

－ 불합격 관리는 검사에서 불합격한 LOT과 상위 히트 불합격으로 못 쓰게 된 LOT을 모아, 불합격 근거와 영향(수주·재생산)을 확인하고 처리 상태와 사유를 기록하는 화면입니다.

## 1. 목적·사용 역할·필요 권한

### 목적

- 검사에서 불합격이 나온 LOT과, 상위 히트가 성분 불합격이라 쓸 수 없게 된 슬래브·코일을 한 곳에 모아 본다. 이 LOT들은 이미 예약·배정·출고 대상에서 빠져 있다 (REQ-INV-007).
- LOT마다 불합격 근거(기준을 벗어난 검사 항목과 측정값)와 영향 범위(연결 수주 품목, 재생산 계획 유무, LOT 이력)를 확인한다.
- 품질 담당이 처리 상태(출하 보류·격리·재작업·조건부 합격·격하·폐기)를 지정하고 사유를 기록한다. 다시 지정해 바꿀 수 있다 (REQ-QC-004, 격리·재작업·조건부 합격은 품질 대시보드 개선 제안으로 추가).
- 처리 상태는 상태와 사유만 기록한다. 격하 재판정·재작업·폐기 재고 처리 같은 후속 로직은 없고, 조건부 합격이어도 재고에 들어가지 않는다 (REQ-QC-004).
- 불합격 LOT에 품질 담당자를 지정해, 대시보드 “처리 필요”에서 미지정·출하 보류·격리·재작업 LOT을 누가 처리할지 보이게 한다.
- 재생산 계획은 여기서 만들지 않는다. 있는지만 보여 주고, 만드는 것은 생산 담당이 생산계획 화면에서 한다 (REQ-PRD-006).

### 사용 역할

| 역할 | 쓰는 방식 | 들어오는 길 |
| --- | --- | --- |
| 품질 (주 사용자) | 불합격 근거와 영향 범위를 확인하고 처리 상태·사유를 지정한다. 품질 담당자를 지정한다 | 왼쪽 메뉴 “불합격 관리”, 대시보드 “처리 필요”·“불합격 처리 상태”·KPI “미처리 불합격”·“출하 보류 LOT”, 불합격 알림, 검사 입력의 판정 결과 |
| 생산 | 불합격 근거와 처리 상태를 보고 재생산 여부를 판단한다 (조회만) | 메뉴에는 없음. 링크·주소로 직접 (불합격 알림은 생산계획 화면으로 온다) |
| 관리자 | 불합격 현황을 확인한다 (조회만) | 메뉴에는 없음. 링크·주소로 직접 |
- 영업·구매·물류는 이 화면을 쓰지 않는다. 주소로 들어오면 “권한 없음” 화면이 나온다. 영업은 불합격 영향을 수주 상세·LOT 추적에서 본다.

### 필요 권한

| 동작 | 필요한 권한 | 기본값으로 가진 역할 |
| --- | --- | --- |
| 불합격 LOT 목록·상세 조회 | DISPOSITION_SET 또는 INSPECTION_REGISTER 조회(VIEW) 이상 | 품질(사용), 생산(INSPECTION_REGISTER 조회), 관리자(조회) |
| 처리 상태 지정·변경 | DISPOSITION_SET 사용(USE) | 품질 |
| 품질 담당자 지정 | INSPECTION_REGISTER 또는 DISPOSITION_SET 사용(USE) | 품질 |
| 담당자 후보 목록 조회 | INSPECTION_REGISTER 또는 DISPOSITION_SET 조회(VIEW) 이상 | 품질, 생산, 관리자 |
| LOT 이력(작업 로그) 조회 | 로그인만 하면 됨 | 모든 역할 |
- 왼쪽 메뉴 “불합격 관리”는 품질 역할 메뉴에만 있고, DISPOSITION_SET 조회 이상일 때 보인다.
- 사용 권한이 없으면 처리 상태 선택·사유 입력·저장 버튼이 비활성이고 “불합격 처리 상태를 지정할 권한이 필요해요”를 보여 준다. 서버도 같은 권한을 다시 확인하고, 없으면 COM-002를 돌려준다.
- 담당자는 사용 중인 품질 역할 사원만 고를 수 있다.
- “사례로 등록”·“비슷한 사례 찾기”는 과거 사례(EX) 기능이라 준비 중이다 (REQ-CASE-002).
- 권한은 역할별 기본값이며 관리자가 “부서·권한”에서 바꿀 수 있다 (역할별 메뉴 v2 3장).

## 2. 철강 흐름에서의 위치

### 흐름

검사 입력(불합격 판정) → **불합격 관리**(근거·영향 확인, 처리 상태 지정) → 생산계획(재생산, 생산 담당) · 대시보드(처리 필요·출하 보류) · 과거 사례(EX, 준비 중)

### 받는 것

| 무엇 | 어디서 | 목록에 오는 조건 |
| --- | --- | --- |
| 자체 불합격 LOT (히트·슬래브·코일) | 검사 입력 — 측정값 등록 후 자동 판정 | 자기 검사가 불합격(`is_passed` = false) |
| 히트 불합격으로 못 쓰는 슬래브·코일 | 검사 입력 — 상위 히트의 성분 검사 불합격 | 상위 히트가 불합격이면 자기 검사가 합격이거나 검사 전이어도 올라온다 (원인 = 히트 불합격) |
| 불합격 근거 | 검사 기록 | 자체 불합격은 그 LOT의 검사, 히트 불합격은 상위 히트의 성분 검사. 기준을 벗어난 항목·측정값·판정 때 기준 |
| 영향받는 수주 품목 | 수주 | LOT에 연결된 수주 품목, 없으면(히트 등) 생산계획의 수주 품목 |
| 재생산 계획 | 생산계획 | 그 수주 품목에 취소되지 않은 재생산 계획이 있으면 가장 최근 것 |
| LOT 이력 | 작업 로그 | 그 LOT의 실적·검사·불합격·배정 해제·처리 상태 이벤트 |
| 품질 담당자 | 검사 입력 또는 이 화면에서 지정 | 선택 (없어도 처리 상태는 지정할 수 있다) |
- 불합격 LOT은 판정이 끝난 시점에 이미 재고·예약·배정·출고 대상에서 빠져 있고, 히트 불합격이면 하위 LOT의 확정 배정도 해제된 뒤다 (검사 입력에서 처리).
- 처음 올라올 때 처리 상태는 “미지정”이고, 품질 부서에 “LOT … 불합격” 알림이 간다.

### 넘기는 것

| 무엇 | 넘어가는 것 | 다음 화면·담당 |
| --- | --- | --- |
| 처리 상태·사유·지정 시각 | LOT의 처리 상태(`disposition_status`), 사유, 지정 시각 | 대시보드(처리 필요 큐, 불합격 처리 상태·체류일, KPI 미처리 불합격·출하 보류 LOT, 품질 상태 재고, 품질 이슈 납기 위험), LOT 추적 상세 |
| 처리 상태 변경 기록 | 작업 로그 DISPOSITION_SET (변경 전·후 상태와 사유) | 작업 로그, LOT·수주 타임라인 (영업도 수주에서 볼 수 있음) |
| 품질 담당자 | LOT의 품질 담당자, 새 담당자에게 알림 | 대시보드 “처리 필요” (품질) |
| 재생산 필요 여부 판단 자료 | 불합격 근거·영향 수주 품목·재생산 계획 유무 (이 화면은 계획을 만들지 않는다) | 생산계획 (생산): 부족 매수를 확인해 재생산 계획 생성 (REQ-PRD-006) |
| 영향 범위 추적 | LOT번호 | LOT 추적(정추적): 이 LOT이 어디까지 퍼졌는지 (REQ-LOT-005) |
| 과거 사례 | 처리 상태 지정 뒤 사례 등록 | 과거 사례 (EX, 준비 중 — REQ-CASE-002) |
- 처리 상태를 지정해도 재고·예약·배정·생산계획은 바뀌지 않는다 (REQ-QC-004). 조건부 합격이나 격하여도 재고에 들어가거나 출고되지 않는다.
- 처리 상태 지정은 알림을 보내지 않는다. 실시간 주제 `lots`·`quality-inspections`로 다른 화면·대시보드가 다시 조회한다.

## 3. 화면에 표시할 데이터

| 영역 | 필드 | 타입·단위 | 출처 API |
| --- | --- | --- | --- |
| 불합격 LOT 목록 (왼쪽) — 상단 | 전체 건수, 처리가 남은 상태 타일 4개(미지정·출하 보류·격리·재작업)별 건수 | 정수, 건 (화면에서 셀) | `GET /api/v1/quality-inspections/rejected-lots` |
| 불합격 LOT 목록 (왼쪽) — 필터 | 처리 상태 칩(전체·미지정·출하 보류·격리·재작업·조건부 합격·격하·폐기)과 건수, 원인 칩(모든 원인·자체 불합격·히트 불합격), LOT·히트 번호 검색 | 코드 DISPOSITION_STATUS 라벨 / 정수, 건 | 위와 같음 (화면에서 거름) |
| 불합격 LOT 목록 (왼쪽) — 줄 | LOT번호 `lotNo`, LOT 유형 `lotType`, 처리 상태 `dispositionStatus`, 강종 `steelGradeCode`·규격 `specCode` | 문자열 / 코드 LOT_TYPE 라벨 / 코드 DISPOSITION_STATUS 라벨, null = 미지정 | 위와 같음 |
| 불합격 LOT 목록 (왼쪽) — 줄 | 불합격 원인 `rejectedBy`(자체·히트), 불합격 항목명 `failedInspection.failedItems[].inspectionItemName`, 히트 불합격이면 히트 번호 `heatLotNo` | OWN · HEAT / 문자열 | 위와 같음 |
| 불합격 LOT 목록 (왼쪽) — 줄 | 영향 수주 품목 `affectedSalesOrderItem.salesOrderNo`·`lineNo`, 재생산 계획 유무 `hasReproductionPlan` | 문자열·정수, 없으면 “연결 수주 없음” / boolean | 위와 같음 |
| 상세 머리 | LOT번호(LOT 추적 링크), LOT 유형, 처리 상태 배지, 원인 배지(자체 검사 불합격 / 상위 히트 불합격) | 문자열 / 배지 | 목록 응답의 선택한 LOT. 목록에 없는 LOT(`?lot=`)이면 “이 LOT은 불합격 목록에 없어요” |
| LOT 정보 카드 | 강종·규격, 불합격 원인(히트 불합격이면 히트 번호 링크), 상위 히트 `heatLotNo`(슬래브·코일만), 생산계획 `productionPlanNo`, 생산 시각 `producedAt` | 문자열, 없으면 “없음” / ISO 시각 | 목록 응답 |
| LOT 정보 카드 | 근거 검사: 검사번호 `failedInspection.qualityInspectionNo`, 검사 공정 `processCode`, 검사 시각 `inspectedAt` | 문자열 / 코드 PROCESS_CODE 라벨 / ISO 시각, 없으면 “기록 없음” | 목록 응답의 `failedInspection` |
| LOT 정보 카드 | 영향받는 수주 품목: 수주번호(링크)·품목 줄, 고객사 `customerName`, 납기 `dueDate`와 D-n, 주문 매수 `orderedQty`, 품목 상태 `salesOrderItemStatus` | 문자열 / 날짜 / 정수, 매·개 / 코드 SALES_ORDER_ITEM_STATUS 라벨. 없으면 “연결된 수주 품목이 없어요” | 목록 응답의 `affectedSalesOrderItem` |
| 검사값 | 검사번호, 불합격 항목 수 / 전체 항목 수, 검사 판정 배지 | 문자열 / 정수, 개 / 코드 INSPECTION_RESULT | `GET /api/v1/quality-inspections/:id` (근거 검사 id) |
| 검사값 | 항목별 표: 항목명, 기준(판정 때 저장된 min·max), 측정값과 단위, 항목 판정, 기준 안 위치(불합격 항목은 빨간색) | 숫자 문자열 / boolean, null = 입력 안 한 선택 항목 | 위와 같음 (`values[]`) |
| 검사값 | 히트 불합격이면 “이 LOT 자신이 아니라 상위 히트 …의 성분 검사 결과예요” 안내 | 문구 | 목록 응답의 `rejectedBy` |
| 검사값 | 상세 검사를 못 불러오면 불합격 항목만 표시: 항목명, 측정값·단위, 기준 | 문자열 / 숫자 문자열 | 목록 응답의 `failedInspection.failedItems` |
| 담당 · 처리 | 품질 담당자 `qualityAssigneeId`, 담당자 선택 목록(이름·직급) | 사원 ID / 문자열 | 목록 응답, `GET /api/v1/quality-inspections/assignees` |
| 처리 상태 지정 | 현재 처리 상태, 지정 시각 `dispositionAt`, 사유 `dispositionReason` | 코드 DISPOSITION_STATUS 라벨 / ISO 시각 / 문자열, 미지정이면 “아직 처리 상태를 지정하지 않았어요” | 목록 응답 |
| 처리 상태 지정 | 고를 수 있는 상태 6개와 설명(출하 보류·격리·재작업·조건부 합격·격하·폐기), 사유 입력 글자 수(최대 500자) | 코드 DISPOSITION_STATUS / 정수, 자 | 공통코드(shared) — API 없음 |
| 영향과 자동 처리 | 불합격 판정 때 시스템이 한 것: 예약·배정·출하 대상에서 제외, (히트면) 하위 슬래브·코일 사용 불가 | 고정 문구 (LOT 유형에 따라) | 목록 응답의 `lotType` |
| 영향과 자동 처리 | 재생산 계획: 계획번호 `reproductionPlan.productionPlanNo`(링크), 계획 상태 `productionPlanStatus`, 부족 매수 `shortageQty` | 문자열 / 코드 PRODUCTION_PLAN_STATUS 라벨 / 정수, 매·개. 없으면 “재생산 계획이 아직 없어요”, 수주 품목이 없으면 “재생산 계획 대상이 아니에요” | 목록 응답의 `reproductionPlan` |
| 이력 | 이 LOT의 최근 이벤트 8건: 시각, 주체(사용자 이름 또는 시스템), 이벤트 라벨, 요약 | ISO 시각 / 문자열 | `GET /api/v1/business-events?lotId=&limit=100` |
- 목록·상세의 대부분은 `GET /api/v1/quality-inspections/rejected-lots` 한 번으로 온다(`GET /api/v1/lots/rejected`와 같은 응답). 생산 시각 최신순.
- 시각은 ISO 문자열이며 화면에는 한국 시간으로 표시한다. 기준·측정값은 소수 4자리까지의 숫자 문자열이고 화면에서는 뒤의 0을 지워 보여 준다.
- 조회 권한: 불합격 목록은 DISPOSITION_SET 또는 INSPECTION_REGISTER 조회 이상, 검사값 상세(`/quality-inspections/:id`)는 INSPECTION_REGISTER 조회 이상, 이력은 로그인 사원.

## 5. 상태 변화·작업 로그

### 상태 변화

| 대상 (테이블·컨럼) | 언제 | 변화 |
| --- | --- | --- |
| 처리 상태 `lot.disposition_status` | 처리 상태 지정 | null(미지정) 또는 이전 상태 → HOLD(출하 보류) · QUARANTINED(격리) · REWORK(재작업) · CONDITIONAL_PASS(조건부 합격) · DOWNGRADED(격하) · SCRAPPED(폐기). 어느 상태에서든 다시 지정할 수 있고, 미지정으로 되돌리는 기능은 없다 |
| 사유 `lot.disposition_reason` | 처리 상태 지정 | 입력한 사유로 덮어쓴다 (이전 사유는 작업 로그에만 남는다) |
| 지정 시각 `lot.disposition_at` | 처리 상태 지정 | 지금 시각. 같은 상태로 사유만 다시 기록해도 새 시각이 된다 → 대시보드 체류일이 이 시각부터 다시 센다 |
| 품질 담당자 `lot.quality_assignee_id` | 담당자 저장 | 고른 사원으로 바꾼다 (null이면 미배정). 처리 상태에는 영향 없음 |
| 재고·예약·배정·LOT 상태·판정·생산계획 | — | 바뀌지 않는다 (REQ-QC-004). 불합격 LOT은 판정 때 이미 제외돼 있고, 조건부 합격·격하여도 재고에 들어가지 않는다. 폐기여도 LOT 상태(`lot_status`)는 그대로다 |
- 처리 상태에 따라 대시보드에서 보이는 곳이 달라진다. 미지정·출하 보류·격리·재작업은 “처리가 남은 상태”로 “처리 필요” 큐에 남고, 조건부 합격·격하·폐기는 큐에서 빠진다. 출하 보류는 KPI “출하 보류 LOT”에 센다.
- 처리 상태 지정은 한 트랜잭션이다: LOT 잠금 → 불합격 LOT인지 다시 확인 → 상태·사유·시각 저장 → 작업 로그. 끝나면 실시간 주제 `lots`·`quality-inspections`를 보낸다.

### 작업 로그

| 이벤트 (화면 라벨) | 언제 | 주체 | 대상·연결 | 내용 |
| --- | --- | --- | --- | --- |
| DISPOSITION_SET (처리 상태) | 처리 상태를 지정할 때마다 (같은 상태로 사유만 다시 기록해도) | USER (지정한 품질 담당) | 대상 = LOT(LOT번호). LOT 타임라인, 연결 수주가 있으면 수주 타임라인에도 나온다 | “LOT… 불합격 처리 상태: 출하 보류”. 변경 전·후 처리 상태와 사유, 사유 코드 QUALITY_FAILURE, 입력한 사유 |
- 담당자 저장은 작업 로그를 남기지 않는다 (REQ-LOG-002 이벤트 종류에 없음).
- 이 화면의 “이력”에 보이는 검사(INSPECTION_REGISTERED)·불합격(REJECTED_JUDGED)·배정 해제(ALLOCATION_RELEASED)는 검사 입력에서 생긴 것이다. 이 화면이 만드는 작업 로그는 DISPOSITION_SET 하나다.
- 작업 로그는 처리 상태 저장과 같은 트랜잭션에서 저장된다 (REQ-LOG-001).
