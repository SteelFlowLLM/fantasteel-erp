## 2. 네이밍

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| 서버 파일 | kebab-case + NestJS 역할 접미사 | `reservation.service.ts`, `create-sales-order.dto.ts` |
| 클래스 | PascalCase + 역할 | `ReservationService`, `SalesOrderController` |
| DTO | 동사 + 대상 + Dto | `CreateSalesOrderDto`, `ConfirmGoodsIssueDto` |
| Next.js 라우트 파일 | Next.js 규칙, 폴더는 kebab-case | `app/sales-orders/page.tsx`, `layout.tsx` |
| React 컴포넌트 파일 | PascalCase | `SalesOrderTable.tsx` |
| 훅 | use + camelCase | `useSalesOrderList.ts` |
| 변수·함수 | camelCase, 함수는 동사 시작 | `confirmAllocation()` |
| 타입 | PascalCase, `I` 접두사 없음 | `SalesOrderItem` |
| 상수 | UPPER_SNAKE | `DEFAULT_HEAT_CAPACITY_TON` |
| 환경변수 | UPPER_SNAKE, 브라우저 노출 변수는 `NEXT_PUBLIC_` | `NEXT_PUBLIC_API_BASE_URL` |
| DB 테이블·컬럼 | snake_case 단수 (용어 사전 DB명) | `sales_order`, `reserved_qty`, `lot_relation`, `business_event` |
| API URL | kebab-case, 복수 명사 | `/api/v1/sales-orders/:id/reservations` |
- `[강제]` 도메인 영문명·변수명·DB명은 용어 사전을 따른다 (`heat`, `slab`, `hotMetal`, `millSheet`, `purchaseRequisition`, `scheduledReceiptTon`, `specificConsumption`, `goodsIssue` …). 용어 사전에 없는 이름이 필요하면 용어 사전에 먼저 추가한다
- `[강제]` 용어 사전의 동의어(사용 금지) 칸에 있는 단어는 그 용어를 가리키는 이름(변수·함수·테이블·컬럼)으로 쓰지 않는다. 다른 개념의 이름이나 코드 값으로는 쓸 수 있다(예: 배정의 `allocation`, LOT 상태 값 `SHIPPED`). `order` 단독 사용 금지 → `salesOrder` / `purchaseOrder`
- `[강제]` 단위를 이름에 포함: 매수는 `Qty`, 톤은 `Ton` (`reservedQty`, `theoreticalWeightTon`, `requiredTon`)
- `[강제]` 제품(슬래브·코일) 수주·재고의 톤은 저장하지 않고 매수 × 1매 이론중량으로 계산한다(REQ-SO-002, REQ-INV-001). 제품 테이블에 톤 합계 컬럼을 만들지 않는다
- `[권장]` Boolean은 `is`/`has` 접두사, 날짜는 `Date`, 시각은 `At` 접미사 (`isPassed`, `dueDate`, `confirmedAt`)

## 3. Supabase 사용 규칙

- `[강제]` 업무 데이터(`public` 스키마)는 NestJS API로만 읽고 쓴다. 프론트에서 supabase-js로 업무 테이블에 직접 접근하지 않는다. 권한 검증, 작업 로그, AI 안전 규칙이 서버에 있기 때문이다(REQ-AUTH-003, REQ-LOG-001, REQ-AST-004)
- `[강제]` `SUPABASE_SERVICE_ROLE_KEY`와 DB 접속 문자열은 NestJS 서버에서만 쓴다. `NEXT_PUBLIC_` 변수로 노출하지 않는다
- `[강제]` 스키마는 Prisma Migrate로만 바꾼다. Supabase 대시보드 Table Editor, `supabase db diff`, `supabase/migrations`로 스키마를 바꾸지 않는다. Prisma는 `public` 스키마만 관리하고 `auth`·`storage` 등 Supabase 관리 스키마는 건드리지 않는다
- 로컬 개발: Docker 실행 후 `supabase start`로 로컬 스택을 띄운다. 로컬 DB는 `localhost:54322`, Studio는 `localhost:54323`
- Supabase 기능 사용 범위

| 기능 | 결정 | 관련 요구사항 |
| --- | --- | --- |
| Auth | 사용 안 함. NestJS 자체 JWT로 사원번호·비밀번호 로그인 (6장) | REQ-AUTH-001 |
| Storage | 메시지 첨부·밀시트 PDF 저장에 사용. 업로드와 서명 URL 발급은 서버에서 | REQ-MSG-003, REQ-SHP-004 |
| Realtime | 사용 안 함. NestJS WebSocket Gateway로 메신저 실시간 송수신 | REQ-MSG-002 |

## 4. 공통코드

- `[강제]` 코드 값과 한글 표시명은 [공통 코드 정의서](%EA%B3%B5%ED%86%B5%20%EC%BD%94%EB%93%9C%20%EC%A0%95%EC%9D%98%EC%84%9C%203ecfd862227080ad9553d6bcb92522f9.md)를 따른다. 새 코드는 공통코드 정의서에 먼저 추가한 뒤 `shared/`에 반영한다
- `[강제]` 상태값은 `shared/src/codes/`에 값·타입·한글 표시명을 한 번만 정의하고 server·client가 import한다. 상수 이름은 공통코드 정의서의 코드 그룹 ID와 같게 한다. DB 컬럼은 String이며 Prisma enum은 쓰지 않는다
- `[강제]` 서버는 DTO에서 `@IsIn(Object.values(RESERVATION_STATUS))`처럼 검증하고, 상태 변경은 service에서만 한다
- `[강제]` 공통코드 값을 저장하는 String 컨럼의 이름은 코드 그룹 ID를 소문자로 그대로 쓴다 (예: ALLOCATION_PURPOSE → `allocation_purpose`, LOT_RELATION_EVIDENCE → `lot_relation_evidence`, BUSINESS_EVENT_TYPE → `business_event_type`). 상태 컨럼의 `{대상}_status` 규칙도 이 규칙에 포함된다. 단 ROLE·STEEL_GRADE는 테이블(`role`, `steel_grade`)로 관리하므로 코드 값은 `role_code`·`steel_grade_code`에 두고, 다른 테이블은 `{테이블}_id` 컨럼으로 참조한다 (논리 참조, DB FK 제약 없음, 7-2)
- 공통코드 테이블·API는 만들지 않는다. 관리자가 직접 바꿔야 하는 표시용 분류가 생기면 그 코드에만 추가한다
- `[권장]` 핵심 상태 컬럼(예약·배정·초안)은 마이그레이션에 CHECK 제약을 추가한다

```tsx
// shared/src/codes/reservation-status.ts
export const RESERVATION_STATUS = {
  ACTIVE: 'ACTIVE',
  CONVERTED: 'CONVERTED',
  RELEASED: 'RELEASED',
} as const;
export type ReservationStatus =
  typeof RESERVATION_STATUS[keyof typeof RESERVATION_STATUS];

export const RESERVATION_STATUS_LABEL: Record<ReservationStatus, string> = {
  ACTIVE: '예약중',
  CONVERTED: '출고 전환',
  RELEASED: '해제',
};
```

## 5. API

- `[강제]` 경로는 `/api/v1` + kebab-case 복수 명사. 상태 변경은 액션 URL `POST /:id/동작` (예: `POST /api/v1/shipment-requests/:id/issue`). 계산 조회처럼 리소스가 아닌 경로는 예외로 둔다(예: `GET /api/v1/mrp/requirements`)
- `[강제]` 응답 포맷. 성공 응답은 전역 인터셉터, 실패 응답은 전역 예외 필터에서 만든다

```tsx
{ success: true, data: {...} }
{ success: false, error: { code: 'SO-002', message: '수량은 1 이상의 정수로 입력해 주세요' } }
```

- `[강제]` 에러는 `AppException(code, message, httpStatus)`을 throw한다. 컨트롤러별 try/catch 응답 금지
- `[강제]` 에러 코드는 `영역-번호`. 영역은 요구사항 영역 코드를 쓴다 (`SO-001`, `INV-003`, `PUR-002`). 공통 에러는 `COM-`
- `[강제]` 요청 검증은 class-validator 데코레이터를 붙인 DTO + 전역 ValidationPipe(`whitelist`, `forbidNonWhitelisted`, `transform` 활성화)
- `[강제]` 톤 등 Decimal 값은 응답에서 문자열로 변환한다
- 페이징 `page`, `size`, `sort` / 날짜·시각 ISO 8601
- `[강제]` 시각은 `timestamptz`로 저장하고 화면에서 Asia/Seoul로 표시한다. 날짜만 의미 있는 값(납기일, 희망 입고일, 생산완료일)은 `date` 타입으로 저장한다
- `[강제]` LOT 채번의 `YYMMDD`와 "오늘" 계산(납기 위험 등)은 서버에서 Asia/Seoul 기준으로 한다

## 6. 레이어 (NestJS)

| 레이어 | 역할 |
| --- | --- |
| module | 의존성 조립 |
| controller | 라우팅, DTO 검증, 가드 적용. 업무 로직 금지 |
| service | 업무 로직, 트랜잭션, 데이터에 따른 권한 검사 |
| repository | DB 접근 (유일) |
- `[강제]` 트랜잭션은 service에서 `this.prisma.$transaction(async (tx) => ...)` — 수주 등록, 예약, 배정, 출고 확정, 입고 확정
- `[강제]` 예약 생성·전환·해제와 `reserved_qty` 갱신은 같은 트랜잭션에서 한다(REQ-INV-009)
- `[강제]` 권한: 컨트롤러에 인증 가드와 권한 가드(`@RequirePermission(PERMISSION.X, 'USE')`)를 적용한다. 승인은 권한 코드가 아니라 service에서 "요청자 소속 부서의 부서장인가"로 검사한다(REQ-AUTH-004)
- `[강제]` 로그인은 사원번호·비밀번호. 비밀번호는 bcrypt 해시로 저장하고 평문 저장·로그 출력 금지
- `[강제]` 인증은 `@nestjs/jwt`로 발급한 access token을 httpOnly 쿠키(`Secure`, `SameSite=Lax`)로 내려주고, 인증 가드에서 쿠키의 토큰을 검증한다. CORS는 프론트 origin만 허용하고 `credentials: true`로 둔다. 토큰 만료·갱신 방식은 비기능 요구사항 결정 후 정한다
- `[강제]` 메신저 실시간 송수신은 messenger 모듈의 WebSocket Gateway로 하고, 연결(handshake) 시 쿠키의 access token을 검증한다
- `[강제]` 작업 로그는 본 거래와 같은 트랜잭션에서 저장한다(REQ-LOG-001)
- `[강제]` 작업 로그는 service에서 `businessEventRecorder.record(tx, {...})`로 직접 기록한다. 이벤트 발행 방식은 쓰지 않는다
- `[강제]` 응답은 Prisma 모델을 그대로 내보내지 않고 매퍼 함수(예: `toSalesOrderResponse`)로 응답 DTO를 만든다. 톤 계산값 추가, Decimal 문자열 변환, 비밀번호 해시 등 내부 컬럼 제외를 여기서 한다
- `[권장]` 응답 타입은 `shared/`에 두어 프론트와 함께 쓴다

## 7. Prisma

### 7-1. 연결 (Prisma 7 + Supabase)

| 환경변수 | 용도 | 원격 Supabase | 로컬 |
| --- | --- | --- | --- |
| `DATABASE_URL` | 앱 실행(Prisma Client) | Transaction pooler(6543) + `?pgbouncer=true` | `localhost:54322` |
| `DIRECT_URL` | Prisma CLI (`migrate`, `generate --sql`) | Direct 연결 또는 Session pooler(5432) | `localhost:54322` |

```tsx
// server/prisma.config.ts — Prisma CLI는 직접 연결 사용
import 'dotenv/config';
import { defineConfig, env } from 'prisma/config';

export default defineConfig({
  schema: 'prisma/schema.prisma',
  migrations: { path: 'prisma/migrations', seed: 'tsx prisma/seed.ts' },
  datasource: { url: env('DIRECT_URL') },
});
```

```jsx
// server/prisma/schema.prisma
generator client {
  provider        = "prisma-client"
  output          = "../src/generated/prisma"
  previewFeatures = ["typedSql"]
}

datasource db {
  provider     = "postgresql"
  relationMode = "prisma"
}
```

```tsx
// server/src/prisma/prisma.service.ts — 앱은 풀러 URL + 드라이버 어댑터
import { Injectable, OnModuleInit, OnModuleDestroy } from '@nestjs/common';
import { PrismaPg } from '@prisma/adapter-pg';
```

### 7-2. 스키마

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| 모델명 | PascalCase 단수 | `Reservation` |
| 테이블명 | `@@map` snake_case 단수 (용어 사전 DB명) | `@@map("reservation")` |
| 필드명 / 컬럼명 | camelCase / `@map` snake_case | `reservedQty @map("reserved_qty")` |
| FK 필드 | `{관계명}Id` | `salesOrderItemId` |
| 관계 필드 | 단수 = 모델명, 복수 = 복수형 | `salesOrderItem`, `reservations` |

```jsx
model Reservation {
  id               Int      @id @default(autoincrement())
  salesOrderItemId Int      @map("sales_order_item_id")
  itemId           Int      @map("item_id")
  reservedQty      Int      @map("reserved_qty")
  reservationStatus String  @default("ACTIVE") @map("reservation_status") // RESERVATION_STATUS (shared)
  createdAt        DateTime @default(now()) @map("created_at") @db.Timestamptz(3)
  updatedAt        DateTime @updatedAt @map("updated_at") @db.Timestamptz(3)

  salesOrderItem SalesOrderItem @relation(fields: [salesOrderItemId], references: [id])
  item           Item           @relation(fields: [itemId], references: [id])

  @@index([salesOrderItemId])
  @@index([itemId])
  @@map("reservation")
}
```

- `[강제]` `@map` / `@@map` 누락 금지
- `[강제]` 상태 컬럼명은 `{대상}_status`로 한다 (예: `reservation_status`, `allocation_status`, `lot_status`). 용어 사전에 DB명이 정해진 상태 컬럼은 그 이름을 따른다(예: `draft_status`, `disposition_status`)
- `[강제]` 모든 모델에 `createdAt`, `updatedAt`
- `[강제]` 톤 등 소수값은 `Decimal` (`@db.Decimal(12, 3)`), `Float` 금지
- `[강제]` 매수(qty)는 `Int`
- `[강제]` 업무번호(LOT 번호, 수주번호 등)는 PK와 별도 `@unique` 컬럼
- `[강제]` 원료·슬래브·코일은 단일 `item` 테이블(`item_type`)로 관리한다. 제품은 `item_type`·강종·두께·폭·길이 조합에 `@@unique`를 걸고, 유형별 필수 컬럼은 CHECK 제약으로 보장한다. 사용된 규격의 치수·이론중량 수정은 service에서 막는다(REQ-MST-003)
- `[강제]` 검사 기준은 수정하지 않고 새 버전으로 추가하며, 검사 기록은 `inspection_standard_id`(버전)를 참조한다
- `[강제]` 시각 컬럼은 `@db.Timestamptz(3)`, 날짜 컬럼은 `@db.Date`
- `[강제]` LOT는 단일 `lot` 테이블로 관리한다(`lot_no` unique, `lot_type`). 고로·전로 번호, 원료 잔량(톤) 등 유형별 값은 nullable 컬럼으로 둔다. `lot_relation`·`allocation`은 `lot.id`를 참조한다
- `[강제]` 소프트 삭제 컬럼(`deletedAt`)을 쓰지 않는다. 업무 거래(수주, 예약, 구매요청, 발주, 입고, LOT, 실적, 검사, 출하)는 삭제 API를 만들지 않고 상태(CANCELLED, RELEASED 등)로 끝낸다
- `[강제]` 기준정보(규격, 고객사, 공급업체, 야드, 직급 등)는 참조가 없을 때만 삭제하고, 참조가 있으면 거부한다. 사원은 삭제하지 않고 `isActive`로 퇴사 처리한다
- `[강제]` DB 외래키 제약을 만들지 않는다. 관계는 `@relation`으로 스키마에만 표현하고, ERD에는 FK를 모두 표시한다
- `[강제]` FK 컨럼(`{관계명}Id`)마다 `@@index`를 단다. 복합 unique·인덱스의 첫 컨럼이면 생략할 수 있다
- `[강제]` 생성·수정할 때 참조 대상이 있는지 service에서 확인한다. 요청으로 받은 ID는 반드시 조회해서 확인하고, 없으면 `COM-003`을 반환한다
- `[강제]` 삭제와 FK 컨럼 변경은 Prisma Client로만 하고, 관계에 `onDelete`를 명시한다. 기준정보는 `Restrict`로 둔다. TypedSQL·raw 쿼리로는 삭제나 FK 컨럼 변경을 하지 않는다(흉내가 적용되지 않음)
- `[강제]` 고아 데이터 점검 스크립트(`server/scripts/check-orphans`)를 두고 시드 후와 PR 전에 실행한다

### 7-3. 마이그레이션

- `[강제]` 공유 반영은 로컬 Supabase에 `prisma migrate dev`로만 한다. `db push`는 개인 로컬 실험용
- `[강제]` 원격 Supabase 반영은 `prisma migrate deploy`
- `[강제]` 커밋된 마이그레이션 파일 수정 금지 → 새 마이그레이션으로
- 이름: snake_case 동사구 (`add_reservation`)
- `[강제]` 스키마 담당자 1명이 `schema.prisma`와 마이그레이션을 관리한다. 담당: 정건희 / 보조: 생산·재고·LOT 담당
- ERD 단계에서 1차 스키마(P1 테이블 전체)는 담당자가 한 번에 작성한다
- 이후 변경은 팀원이 이슈나 PR 설명으로 요청하고, 담당자가 `schema.prisma`와 마이그레이션을 만든다
- 스키마 PR은 하루 한두 번 묶어서 머지한다. 머지 전 develop을 rebase하고, 마이그레이션이 겹치면 담당자가 재생성한다

## 8. 쿼리 관리

| 쿼리 유형 | 작성 방법 | 위치 |
| --- | --- | --- |
| 단건 조회·등록·수정·삭제 | Prisma Client | `{도메인}.repository.ts` |
| 조건 검색(동적 필터·페이징) | Prisma Client (`where` 조건부 조립) | `{도메인}.repository.ts` |
| 복잡한 쿼리 | TypedSQL | `prisma/sql/{동사}{대상}.sql` |

**복잡한 쿼리 기준** (하나라도 해당)

- 집계(GROUP BY, 윈도우 함수) — MRP 순소요, 수주 충족 현황, 대시보드 통계
- 3개 이상 테이블 JOIN 또는 서브쿼리 — LOT 정·역추적
- 락 필요 (`SELECT ... FOR UPDATE`) — 재고 풀 잠금
- Prisma Client로 표현 불가하거나 N+1 발생
- 애매하면 PR 리뷰어가 판단

**규칙**

- `[강제]` DB 접근은 repository에서만. service·controller에서 PrismaService 직접 쿼리 금지 (트랜잭션 시작만 예외)
- `[강제]` `$queryRaw` 인라인 SQL 금지, `$queryRawUnsafe` 금지
- `[강제]` repository 함수 첫 인자는 `tx`
- SQL 파일명은 camelCase 동사구 (`getReservedQtyBySpec.sql`), 상단에 목적 주석 한 줄
- 파라미터는 `-- @param {타입} $1:이름`으로 명시
- 스키마 변경 시 `migrate dev` → `generate --sql` 실행 (로컬 Supabase가 떠 있어야 함)
- `[권장]` `select` / `include` 명시
- `[강제]` 동시성 처리는 대상별로 정한다
    - 예약 매수: 조건부 update 한 줄 (`UPDATE inventory SET reserved_qty = reserved_qty + :n WHERE id = :id AND on_hand_qty - reserved_qty >= :n`). 바뀐 행이 0이면 `INV-001`
    - LOT 중복 배정: `allocation(lot_id)`에 `WHERE allocation_status = 'CONFIRMED'` 부분 unique 인덱스. 마이그레이션 SQL에 직접 추가
    - 여러 행을 함께 검증하는 처리(출고 확정 등): `SELECT ... FOR UPDATE` (TypedSQL)

```sql
-- prisma/sql/getReservedQtyBySpec.sql
-- 수주별 규격 예약 매수 합계(ACTIVE)
-- @param {Int} $1:salesOrderId
SELECT r.item_id, SUM(r.reserved_qty) AS reserved
FROM reservation r
JOIN sales_order_item i ON i.id = r.sales_order_item_id
WHERE i.sales_order_id = $1
  AND r.reservation_status = 'ACTIVE'
GROUP BY r.item_id;
```

```tsx
// inventory.repository.ts
import { Prisma } from '../../generated/prisma/client';
import { getReservedQtyBySpec } from '../../generated/prisma/sql';

export const findReservedQtyBySpec = (tx: Prisma.TransactionClient, salesOrderId: number) =>
  tx.$queryRawTyped(getReservedQtyBySpec(salesOrderId));
```

## 9. 프론트 (Next.js)

- `[강제]` `@/` alias 사용, `../../../` 금지 (`tsconfig` paths)
- `[강제]` Next.js 서버 코드(Route Handler, Server Action)에서 DB·Prisma에 직접 접근하지 않는다. 업무 데이터는 NestJS API로만 (3장)
- `[강제]` API 호출은 `api/` 함수 + 커스텀 훅으로만. 컴포넌트에서 fetch·axios 직접 호출 금지
- `[강제]` 데이터를 다루는 화면은 클라이언트 컴포넌트(`'use client'`)로 만들고 TanStack Query로 NestJS를 호출한다. 서버 컴포넌트는 레이아웃·메뉴 등 데이터 없는 부분에만 쓴다
- `[강제]` 인증 토큰은 프론트 코드에서 다루지 않는다(localStorage 저장 금지). API 호출은 `credentials: 'include'`로 쿠키를 함께 보낸다(6장)
- `[강제]` 서버 상태는 TanStack Query, 클라이언트 상태는 Zustand. 서버 데이터를 전역 스토어에 복사 금지
- `[권장]` 저장·확정 후에는 관련 쿼리를 무효화(`invalidateQueries`)해 목록을 갱신한다. 메신저 WebSocket 수신도 쿼리 캐시를 갱신하는 방식으로 반영한다
- 함수형 컴포넌트 + named export (라우트 파일은 Next.js 규칙대로 default export)
- `[강제]` 스타일은 Tailwind CSS로 작성한다. 인라인 `style` 속성과 별도 CSS 파일은 Tailwind로 표현할 수 없는 경우만 쓴다
